# 05: Apply Note Types, Templates, and shared styling

**What to build:** An author can import YAML Notes whose Note Types do not yet exist, or update retained Card Type Templates and shared styling for existing Note Types. The workflow preserves existing identities and explains effects on every Note sharing an updated Note Type.

**Blocked by:** 01 — Move shared styling to each Note Type; 04 — Add and update Notes directly from YAML.

**Status:** ready-for-agent

**Verification environment:** All implementation tests and manual rendering checks use sandbox Notes/Collections and the dedicated environment documented in [`tools/headless_import/exploration.md`](../../../tools/headless_import/exploration.md). Create fixture Decks/media in setup, not in the updater. No personal Collection access or product backup/restore mechanism.

- [ ] Create missing Note Types from the authoritative schema, approved native tag metadata, ordered Card Types, Front/Back Templates, and single shared stylesheet; then add their YAML Notes to linked existing Decks.
- [ ] For existing compatible Note Types, mutate retained Templates and shared styling while preserving Field/template identities, order, and unrelated metadata.
- [ ] Reject existing Field/Card Type additions, removals, renames, reorderings, or Note Type conversions rather than attempting implicit migrations.
- [ ] Validate all Template Field references and reject conflicting template Deck overrides without silently changing them.
- [ ] Preview and require explicit approval of shared Note Type ownership and Note Type-wide effects, including effects on Notes outside repository entries.
- [ ] Report Cards generated by Front Template changes; do not delete retained empty Cards, Notes, or Templates.
- [ ] Capture Card IDs before Template changes and distinguish newly generated managed Cards from existing Cards and Cards belonging to unrelated Notes. Resolve new managed Card targets from YAML `deck` for ticket 06 placement; never move existing Cards or report their Deck differences. Do not change updater-controlled placement for unrelated generated Cards.
- [ ] Verify rendering, persistence, retained Note/Card identities and review-history rows, and second-run idempotency through the public command in sandbox Collections. Use sandbox Notes for intended-client rendering; close Desktop again before headless operations. No pre-apply backup or automatic restore is introduced.
- [ ] No CSS compilation, Deck creation, media upload, Deck-option changes, or sync automation is introduced.
